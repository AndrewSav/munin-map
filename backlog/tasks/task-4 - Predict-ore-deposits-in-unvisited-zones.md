## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The map shows ore deposits only from saved world objects, and those exist only in zones that have already been generated. Even with `reveal_all = true` (TASK-1 adds planned locations there), ore in unvisited zones stays invisible, and ore is much of what players go looking for.

The game places vegetation, ore deposits included, when it generates a zone, from the world seed and its own placement rules. doc-2 records those rules from the game code (1.0.21). In short:
- Each vegetation type is seeded per zone from the world seed, and Munin runs inside the game, so it can call Unity's random functions and `WorldGenerator` directly. Nothing has to be ported.
- What can't be reproduced directly is blocking: a spot is rejected if it hits an object placed earlier in the same zone. The zone's real terrain differs a little too.
- Copper and buried iron scrap (Swamp) are the most reproducible: fixed draws, and only one rock type placed before each. Wrong calls give extra or missing deposits at real candidate spots, never shifted ones. Tin and obsidian are harder, and silver is the right zone but maybe the wrong place.
- In zones with a randomly rotated location, the rotation isn't fixed by the seed, so a prediction there can't be exact.

Three ways to predict:
1. **Re-run the placement rules in Munin,** approximating the blockers (doc-2).
2. **Let the game generate the zones for real on a throwaway copy of the world,** in a second server process, and read off where the ore landed (doc-2).
3. **Method 2, done once offline on the test server, exported to live:** generate a copy of the live world there, read every deposit from it, and give live Munin the list as a data file it shows as "predicted". No placement code in Munin at all.

Method 2 has now been done at full scale (TASK-27): the test server has a snapshot of this world with every zone generated, by the server's own (Ghost) generation under 1.0.21. It took about 3 hours with Upgrade World's `zones_generate`, plus a 17-minute cleanup run with a local build that waits 120 s instead of 10 s per zone (zones whose location files load slowly the first time were otherwise skipped). Munin on the test server already sees every deposit in it.

What a generated copy can't promise, because it isn't fixed by the seed (1.0.21, read in the code):
- the facing of randomly rotated locations: 16 equally likely angles from Unity's shared random state. That's about 77% of locations by planning quantity (9,549 of 12,454); 21% face down the slope (fixed: troll and frost caves, the Mistlands dvergr structures and others) and 2% don't rotate (Fuling villages, Morkhalla, The Hole, Charred fortresses, the start temple). About 15% of zones hold a location, so about 11% hold a randomly rotated one;
- in those zones, ore near the location's parts can be blocked differently, and for an ore type with a ground-tilt draw (tin, obsidian) one difference shifts the rest of that type's spots in the zone;
- which candidate site a unique location is built at (Haldor, the Bog Witch and Hildir's camp: 10 candidates each; the Forge of Potential): the first candidate zone generated wins.
Everything else in a location is seeded from the world seed and the zone, not the facing: optional objects, chest contents, pickable items, and the interiors of most dungeons. Exceptions: burial chambers and Sunken crypts rotate their interior with the location. The copy must also match live's game version and any world-generation mods, and be regenerated after a game update that changes generation.

Never generate zones on the live world: it can't be fully undone (deleted trader sites, location icons already sent to players).

Ground truth for measuring a prediction: the TASK-27 snapshot, where every zone outside live's explored area was generated by the server under 1.0.21 (live's own older zones may come from older game versions).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
TASK-4.1 spike result (details in doc-2 'Measured'): a client-free generator (patches-tools/zonegen) generated every ungenerated zone of the live copy in about 7.4 minutes with 4 processes (9.2 with start-up, about 3 GB each, no failures; Upgrade World took 3 h + 17 min), about 10x Upgrade World's speed per process, and ran next to a busy test server at low priority without hurting it. Its deposits match the TASK-27 snapshot 99.3% (copper 100%, tin 99.9%, scrap 99.7%, silver 98.7%, obsidian 98.2%); the misses are what the seed doesn't decide (generation order near zone edges, randomly rotated locations).
Recommendation (for the user to decide, criterion #8): the copy method is now practical. Build it as (a) a tool that generates a copy of a world headless and writes its ore deposits to a file (fast and parallel, or slow in the background next to the server), and (b) Munin loading that file and showing the deposits as predicted where the save has no real ones. Re-implementing placement in Munin (method 1) is no longer needed for this server; it would only matter to give predictions with no setup at all.

Caveat on TASK-4.1's background result (raised in review): the 'low-priority generator next to the server doesn't hurt it' finding came from the local test server with nobody connected, whose only load was Munin's sweeps, and its 'alone' window came straight after a restart. A live server with players uses more CPU, and the live machine may have fewer cores and less memory; each generator process needs about 3 GB and takes 2-3 cores when it can. Before trying it on live: check the live machine's spare cores and memory, and repeat the test with fewer cores and a settled baseline. (Done in TASK-4.2.)

TASK-4.2 result, input for criterion #8: the copy method is now a standalone tool, patches-tools/zonegen (Windows and Linux, one self-contained file each). It takes a copy of the world save (or a seed for a fresh world), downloads or reuses the dedicated server and BepInEx, generates every ungenerated zone headless, and writes the ore deposits (or any prefab list) to a CSV. A whole world takes minutes in fast mode and about 1.5 hours as one lowest-priority process on one core, which inside a running server container had no measurable effect on the game server (fps and longest frame unchanged). Accuracy against the TASK-27 snapshot: 99.1-99.3% in every run (copper and tin 99.8-100%, silver 97-98%, obsidian about 98%); a seed-only run matches as well (99.3%), and its location plan matches the save's 99.93% (only Haldor's settled site differs), because that world has never been re-planned. Memory: about 3 GB per process at the peak, mostly game assets, whatever the process count. Safety: memory guard (container-aware), oom_score_adj 1000 on Linux, a job object on Windows, servers quit if the tool dies, incremental output with resume. Cost of the method: a copy of the save, a server install (reused if present), and a rerun after a game update that changes generation or the location version. Still open for #8: Munin loading the file (not started), and whether method 1 is still wanted; nothing decided.

Approach (chosen with the user, 2026-11-23): build all three methods, one active at a time, chosen by a server setting `predict_ore`: `off` (default); `file`, an extract the admin makes with ore-extract (TASK-4.2's zonegen, renamed) on any machine and copies into the world's Munin data folder, no upload through the page; `server`, Munin makes the extract on the server itself in the background, with progress for everyone in the page's server details, resuming after restarts; and `in-place`, Munin works out the placement itself. Why: an extract predicts about 99% of deposits (TASK-4.1/4.2), in minutes with several processes or an hour or two on one low-priority core next to the server; in place needs no setup and no extra process but has to approximate blocking by earlier objects and the zone's terrain, so it is expected to be less exact, though valheim.tools shows the approach can be very accurate. No combining of methods (simpler code, not needed). Real deposits always replace predicted ones; nothing runs or is shown while reveal_all is false. A prediction made for another game version: redone in server mode, otherwise shown with a visible warning on the page. ore-extract becomes part of the product, shipped with releases (TASK-4.3), from a new top-level ore-extract/ folder. Order: the extract methods first (TASK-4.3 to 4.5: most of the work exists, and they give the reference to check in place against), then in place (TASK-4.6), expected to become the usual choice. Consequences: the docs compare the methods (time, memory, accuracy and why in place is less exact) and say how to make an extract by hand and give it to Munin; the extract file format becomes an interface between ore-extract and Munin; in-place work stops for re-evaluation with the user if its accuracy falls short. Scope of the parent criteria: #2-#5 and #7 are met by the subtasks together; #6 (mods) needs care per method: an extract runs the server's game but loads only its own plugin, so world-generation mods are not applied, while in place reads the running server's own data.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
With reveal_all = true and predict_ore = true, the map shows where ore deposits will be in zones nobody has visited yet, to viewers with Spoilers on. Munin works them out itself, inside the game server, by re-running the game's own placement rules with the server's own data: about 99% of deposits right (the same as letting the game generate a copy of the world), usually in under a minute, at the lowest priority, with no noticeable effect on the game server. Real and predicted ore are one layer with two styles; real deposits replace predicted ones once a zone is generated. Built in steps: a headless generator and the ore-extract tool (TASK-4.1/4.2), three prediction modes (TASK-4.3 to 4.6), then down to in-place only once it proved as accurate (TASK-4.7). ore-extract remains as fork tooling for reference extracts and accuracy checks. Follow-ups: DRAFT-10 (what to check after a game update), DRAFT-3 (per-deposit labels).
