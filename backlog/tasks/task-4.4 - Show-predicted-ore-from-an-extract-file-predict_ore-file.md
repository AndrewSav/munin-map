## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
TASK-4 shows predicted ore deposits in zones that are not generated yet. TASK-4's approach (in its notes) is three methods behind one setting, `predict_ore`, and the extract methods come first: ore-extract (TASK-4.2's ore-extract, renamed) already writes every deposit of a generated copy of the world to a CSV with a header (seed, world-generation version, location versions, game version). This task is the part every extract method needs: Munin reading such a file and showing its deposits as predicted. The admin makes the file with ore-extract on any machine and copies it into the world's Munin data folder (no upload through the page).

An extract runs the server's game, but ore-extract's server loads only ore-extract's own plugin, so world-generation mods are not applied; an extract made with another game version may be off after an update that changed generation.

Ref: TASK-4 (approach in its notes, parent criteria #2-#7), TASK-4.2 (output format, accuracy), doc-2.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
1. Server, new src/Patches/PredictedOre.cs: setting `predict_ore` (off | file) bound in [Server] through the fork's Bind hook in Config.cs, sent to the page in config; the extract is ore-extract's CSV as written, at <world data folder>/predicted-ore.csv, read at world start and again when its timestamp changes (no restart); header checked: another seed is refused with a log line, another game version is used with a warning flag; deposits sorted into the same kinds as real ore (the Vegetation.ClassifyName rules), so they get the same colours.
2. Generated zones never show predictions: dropped at load against ZoneSystem.m_generatedZones (covers zones generated between the extract and the server start), and whenever that list grows (polled as the fog does, about once a minute), with a world-revision broadcast so viewers update.
3. Data: data/predicted-ore.json (rev, the game version it was made for, mismatch, compact deposit list), answered through the fork's Access routing; served only when reveal_all is on and the mode is file; on the page it goes through the spoiler filter like other game content: viewers without spoilers see it only on explored ground (with the user: the map shows no game content in unrevealed ground, only admin markers, spawn, raids, players and web pins).
4. Page, one fork-owned ore layer (web/js/predicted-ore.js) for all ore, real and predicted (with the user: they had departed visually and felt bolted on). Two styles that apply to both: classic (default, as upstream's ore: small filled dots in each ore's colour; predicted ones the same dot, hollow) and shapes (a shape per ore, copper circle, tin square, silver diamond, obsidian triangle, muddy scrap pentagon: filled for real, hollow and tinted for predicted; readable when zoomed out). The choice is kept per browser. Real ore comes from a fork endpoint data/ore.json (Vegetation's points of the ore kinds, read through AccessTools, revision from Vegetation's version and the explored area; explored ground only unless reveal_all with the spoiler view, as the vegetation index); predictions from data/predicted-ore.json. Upstream's own ore dots are hidden while the layer draws real ore (one marked line in vegpack.js vegShowMask, on a flag the layer sets). The Ore row drives it all: its checklist applies to real and predicted alike, with "Include predicted" and the style choice in it; no separate Predicted ore row on the WebGL map. The 3D view and the non-WebGL map keep upstream's ore and get no predictions (the non-WebGL map has no Ore row; with the user, for consistency). A line in the server details whenever predictions are in use, and the dismissable version note.
5. Docs: docs/ADVANCED.md settings row, a Predicted ore section (making an extract by hand, where to put it) and the start of the methods comparison; PATCHES.md TASK-4 entry updated.
6. Test on the test server: an extract of the live copy; an extract older than the save (zones generated in between); a mismatched game version; a missing and a malformed file; frame times while loading a whole-world extract; the live switch needs a player walking into new ground (the user, at the end).

2026-11-23, ore layer (with the user): real and predicted ore had departed visually and felt bolted on, so one fork layer (web/js/ore-layer.js) now draws both, Classic (default) or Shapes, chosen in the Ore row; upstream's GPU ore dots off via one marked line in vegpack.js; real ore from a new data/ore.json (Patches/OreLayer.cs, Vegetation's points via AccessTools). "Other ore" dropped from predictions: valheim-data checked 1.0.21 and nothing places MineRock_Copper/Iron/Meteorite/Stone or Pickable_Meteorite; the real row keeps the class for console spawns, mods and old worlds.
Fixes: classic predicted dots at least 2.5 px with a dark edge (invisible zoomed out before); predictions held back until ZoneSystem.LocationsGenerated, so generated zones are pruned before anything is served (they showed for up to 30 s after a restart).
Tests passed on the test server: another world's seed refused, no header refused, 1.0.20 extract shown with mismatch, file removed -> no file, restored -> all shown again; each picked up within 30 s. Docs (ADVANCED.md Predicted ore, settings row, API rows, data folder row) and the PATCHES.md TASK-4 entry written.

Crypt scrap (mudpile2) not predicted, by design: valheim-data traced 1.0.21's code (docs/generation-determinism.md, map-resources.md there). Sunken Crypts face one of 16 random headings (unseeded), and the facing changes the dungeon seed (rounded generator position), the box rejections, the room sequence and count (20-30), and each 60% pile roll is seeded from its room's position; so not even the count per crypt is fixed by the seed. The clumps of real scrap piles on the map are crypts (most real piles lie within 40 m of one). Docs say predictions cover surface ore only.

Dungeon ore (with the user): a player inside a crypt is drawn at real x,z (interiors are 5,000 m straight up), so crypt scrap lines up with them on the map and goes as it is mined. data/ore.json sends it as its own list "i" (y > 1000); the page draws it in Classic only, never in Shapes (never predicted, not on the ground, found by the crypt marker anyway). Documented in ADVANCED.md and PATCHES.md. On the test world all ore in dungeons was muddy scrap.

Frame time: measured on the test server, reading the file took about 32 ms and checking deposits against the generated zones 1.6-4.4 ms, both on the game's thread. Moved both to a worker thread (the game's generated-zone set is copied on the game thread first: under 0.5 ms for a few thousand zones); Munin logs the timings after each read and warns if the copy takes over 5 ms. User checks: the style survives a reload; the mismatch note looked right (dismiss not tried). Non-WebGL map (?gl=0) left for the user.

Non-WebGL map (?gl=0, checked by the user): it has no Ore row (real ore is part of upstream's Trees & rocks), so predictions are left off it too, for consistency (the user); the separate Predicted ore row there is gone.

Before closing: reveal_all = false with predict_ore = file now reads nothing (it used to read and not send): tested, no log line, endpoint {on:false}, no predict_ore in the config.
